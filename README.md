# 보안 동향 월보드

사내 모니터에 24시간 띄우는 보안 동향 월보드다.

설계의 기준은 하나다. **지나가는 사람이 멈추지 않고 3~5초 안에 "지금 긴급한 보안 이슈가
있는지"를 판단할 수 있어야 한다.** 마우스와 키보드 조작은 없다. 글자 크기, 정보 밀도,
갱신 주기를 두고 판단이 필요할 때마다 이 기준으로 정했다.

## 구조

수집기와 뷰어가 분리되어 있고, 둘은 `public/data/feed.json` 파일 하나로만 만난다.

```
수집기(Node)  --->  public/data/feed.json  --->  뷰어(브라우저)
```

이렇게 나눈 이유는 대부분의 RSS 피드가 CORS 헤더를 주지 않아 브라우저에서 직접 받을 수
없기 때문이다. 뷰어는 자기 호스트의 `data/feed.json` 하나만 받고 외부 도메인에는 어떤
요청도 보내지 않는다. `index.html`의 CSP(`connect-src 'self'`)가 이를 강제한다.

```
public/          뷰어. 이 디렉터리만 정적 제공하면 된다
collector/       수집기
  fetchers/      rss.js, atom.js, json.js, bsky.js, feed-xml.js(RSS·Atom 공용 파서)
  http.js        조건부 요청·타임아웃·재시도·동시성 제한
  normalize.js   URL 정규화, 항목 ID, 날짜 파싱, HTML 제거
  dedupe.js      중복 제거 3단계
  score.js       우선순위 스코어링과 배지 판정
  summarize.js   한글 요약(제공자 교체 지점)
  write.js       유효성 게이트 + 원자적 쓰기
cache/           summaries.json(요약 캐시), http.json(ETag)
scripts/         verify-sources.js, serve.js
sources.yml      피드 목록. 소스 추가·교체는 이 파일만 고친다
keywords.yml     긴급 키워드와 배지 키워드
scheduler.js     NAS용 주기 실행기
```

## 빠르게 띄우기

```bash
npm install
npm run collect        # feed.json 생성
npm run serve          # http://localhost:8080 에서 확인
```

`npm run serve`는 개발 확인용 정적 서버다. 운영에서는 nginx가 `public/`을 제공한다.

## 방식 A — NAS Docker (운영 기본)

```bash
mkdir -p data cache
cp .env.example .env    # LLM_API_KEY를 채운다. 요약을 안 쓰면 비워 둬도 된다
docker compose up -d
```

`collector` 컨테이너가 `scheduler.js`로 T1·T2는 15분, T3·T4는 30분마다 수집하고,
`web` 컨테이너(nginx)가 8080 포트로 뷰어를 제공한다. 호스트 cron에 의존하지 않으므로
NAS 기종이나 OS에 상관없이 같은 방식으로 돈다.

컨테이너가 다시 뜨면 스케줄을 기다리지 않고 즉시 한 번 전체를 수집한다. 재부팅 뒤
화면이 비어 있는 시간을 만들지 않기 위해서다.

## 방식 B — GitHub Actions + Pages (예비)

`.github/workflows/collect.yml`이 15분 간격으로 수집해 결과를 커밋한다.
`LLM_API_KEY`는 저장소 Secrets에 넣는다.

**알고 써야 할 제약이 있다.**

- 저장소에 60일간 활동이 없으면 스케줄이 자동으로 꺼진다. 별도 알림이 없어 조용히 멈춘다.
  수집기가 매번 커밋하므로 평소엔 문제가 없지만, 수집이 오래 실패해 커밋이 멈추면
  60일 뒤 스케줄까지 죽는 이중 장애가 된다.
- cron은 UTC다. 한국 시간으로 생각하면 9시간이 어긋난다.
- 최소 간격은 5분이고 정시 실행은 보장되지 않는다. 부하가 높으면 지연되거나 건너뛴다.
  그래서 분을 0으로 두지 않고 7, 22, 37, 52를 쓴다.
- 워크플로 파일은 기본 브랜치에 있어야 동작한다.
- 공개 저장소면 수집 데이터와 소스 목록이 전부 공개된다. 사내에서 어떤 소스를 보는지가
  드러나므로 NAS를 운영 기본으로 한다.

`cache/`는 산출물과 함께 커밋한다. `actions/cache`는 참조가 없으면 만료되어 요약 캐시가
조용히 날아가고, 그러면 모든 기사를 다시 요약하게 되어 바로 무료 한도를 넘긴다.

## 키오스크 PC 설정

```bash
chromium \
  --kiosk \
  --noerrdialogs \
  --disable-infobars \
  --disable-session-crashed-bubble \
  --disable-features=TranslateUI \
  --check-for-update-interval=31536000 \
  http://nas.local:8080/
```

`--disable-session-crashed-bubble`이 중요하다. 정전이나 강제 종료 뒤 재시작하면 복원
말풍선이 화면을 가리고, 닫을 사람이 없으면 그대로 남는다.

함께 꺼야 하는 것들이다.

- 화면 보호기, 자동 절전, 자동 잠금
- OS와 브라우저의 자동 업데이트
- 디스플레이 전원 관리(DPMS)

그리고 켜야 하는 것들이다.

- 자동 로그인
- 브라우저를 자동 시작 항목에 등록

전원만 다시 들어와도 사람 손 없이 화면이 돌아오는 상태가 목표다.

화면은 1920x1080 가로 모니터 전용이다. 다른 해상도에서는 레이아웃이 맞지 않는다.
2.5m 거리 가독성은 43인치 이상에서 성립한다(43인치에서 26px 제목이 약 12.9mm).
32인치처럼 작은 패널에서는 글자가 기준에 못 미친다.

## 소스 교체 절차

피드는 조용히 죽거나 주소를 옮긴다. 아래 순서로 처리한다.

1. **확인한다.**

   ```bash
   npm run verify-sources
   ```

   HTTP 상태, 리다이렉트 여부와 최종 URL, Content-Type, 파싱된 항목 수, 가장 최신 항목의
   발행 시각을 표로 보여준다. 활성 소스가 하나라도 실패하면 종료 코드 1로 끝나므로
   CI에서도 쓸 수 있다.

2. **고친다.** `sources.yml`의 해당 블록만 수정한다. 피드 목록은 코드 어디에도 없다.
   소스 추가는 YAML 블록 하나를 더하는 것으로 끝난다.

   ```yaml
   - id: example
     name: 예시 매체
     tier: T3          # T1 15분 / T2 15분 / T3 30분 / T4 30분
     type: rss         # rss | atom | json | bsky
     url: https://example.com/feed/
     lang: en          # ko면 번역 없이 피드 요약을 그대로 쓴다
     enabled: true
   ```

   리다이렉트가 잡히면 표에 최종 URL이 함께 나온다. 그 주소를 `url`에 직접 적는다.
   `enabled: false`로 두면 수집에서 빠지고 `verify-sources` 표에는 "(비활성)"으로 남는다.

3. **다시 확인한다.** `npm run verify-sources`로 200과 항목 수를 확인한 뒤
   `npm run collect`를 돌린다.

소스는 20개 안에서 유지한다. `robots.txt`가 피드 경로를 막은 사이트는 목록에서 뺀다.

## 긴급 키워드 조정

`keywords.yml`에서 관리한다. 운영하면서 가장 자주 바뀌는 부분이라 코드에 넣지 않았다.

- `urgentKeywords` — 제목에 있으면 스코어 +10
- `activeExploitKeywords` — 제목이나 본문에 있으면 `activeExploit` 배지
- `patchAvailableKeywords` — 제목이나 본문에 있으면 `patchAvailable` 배지

비교는 전부 대소문자를 무시한다. 고친 뒤 다시 수집하면 바로 반영된다.

## 한글 요약

해외 기사에 한 줄 한글 요약을 붙인다. 국내 기사는 번역하지 않고 피드가 준 요약을 쓴다.

제공자는 **Anthropic Claude API**이고 기본 모델은 **`claude-haiku-5-5`**다.

지출을 묶어 두기 위한 장치가 네 겹이다.

1. **캐시** — 항목 하나는 평생 한 번만 요약한다. `cache/summaries.json`에 항목 ID로 저장한다.
2. **배치** — 기사 10건을 한 요청에 묶는다.
3. **실행당 상한** — 한 번 실행에서 최대 5요청(= 50건). 초과분은 다음 주기로 넘긴다.
4. **일일 상한** — `SUMMARY_DAILY_REQUEST_LIMIT`(기본 100)에 닿으면 그날은 요약을 멈춘다.
   수집은 계속한다.

T1 항목은 상한과 관계없이 언제나 요약한다. 가장 중요한 항목이 예산 부족으로 번역되지
않는 상황은 허용하지 않는다.

**요약은 편의 기능이고 원문 제목이 진짜 데이터다.** 키가 없거나 API가 실패하거나 생성
결과가 검사를 통과하지 못하면 요약을 비우고 화면은 원문 제목을 그대로 보여준다.
그 상황이 정상 동작이다. 429(속도 제한)와 안전 분류기 거절도 같은 경로로 처리한다.

### 비용

**Claude API에는 무료 등급이 없다.** 선불 크레딧 기반 종량제다.
Gemini를 쓸 때와 달리 "무료 한도 안에 머무르기"가 아니라 "지출 상한 두기"가 목표다.

신규 기사 하루 200건(= 10건씩 20요청) 기준 추정이다.

| 모델 | 입력 / 출력 (백만 토큰당) | 하루 | 월 |
|---|---|---|---|
| `claude-haiku-5-5` (기본) | $0.10 / $0.50 | 약 $0.02 | **약 $0.7** |
| `claude-sonnet-5-5` | $2.00 / $10.00 | 약 $0.48 | 약 $14 |

추정치이며 모델의 사고(thinking) 토큰량에 따라 달라진다. 실제 금액은 Console에서 확인한다.
**지출 상한은 Console의 결제 설정에서 따로 거는 것을 권한다.** `SUMMARY_DAILY_REQUEST_LIMIT`은
이 프로그램이 스스로 지키는 상한일 뿐이고, 설정이 잘못되면 지켜지지 않는다.

속도 제한(RPM/ITPM/OTPM)은 조직의 사용 등급마다 다르고 공통 표가 없다. Console의 Limits
페이지에서 확인한다. 429를 받으면 그 배치만 건너뛰고 다음 수집 주기에 다시 시도한다.

수집기가 도는 곳에서 `api.anthropic.com`으로 나가는 HTTPS가 열려 있어야 한다.

제공자를 바꾸려면 `collector/summarize.js`의 `callProvider` 하나만 고치면 된다.
사내 게이트웨이를 거친다면 `LLM_ENDPOINT`로 주소만 덮어써도 된다.

## 운영 중 알아둘 것

### 화면이 스스로 말하는 신호

- 상단 오른쪽 **갱신 경과 시간**이 30분을 넘으면 노랑, 2시간을 넘으면 빨강이 되고
  "갱신 중단" 배너가 뜬다.
- 상단 오른쪽 **상태 점**은 소스별 상태다. 초록 `ok`, 노랑 `stale`, 빨강 `failed`.
  `failed`가 있을 때만 소스명을 함께 띄운다. 정상일 때 아무 말도 하지 않는 것이 좋은
  대시보드다.
- 수집기가 뷰어보다 새 스키마를 쓰면 "뷰어 업데이트 필요"가 뜬다.
- `feed.json` 조회가 연속 5회 실패하면 "데이터 연결 끊김"이 뜬다. **기사는 그대로 남는다.**

### 수집 실패는 화면을 비우지 않는다

쓰기 전에 세 가지를 검사한다.

1. 항목이 0건보다 많다.
2. T1 소스 중 최소 한 개가 `ok`다.
3. 항목 수가 직전 파일의 50% 이상이다.

하나라도 실패하면 기존 `feed.json`을 건드리지 않고 사유를 로그에 남긴 뒤 종료 코드 1로
끝낸다. 화면은 직전 데이터로 계속 돌아가고 상단 배지만 경고색으로 바뀐다.

> **주의:** 검사 2 때문에 T1 두 소스가 모두 `ok`가 아니면 수집 결과가 영원히 반영되지
> 않는다. `stale`은 `ok`가 아니다. CISA KEV는 며칠에 한 번 묶어서 등재하므로 평상시에도
> `stale`로 표시되는 날이 많다. KNVD까지 24시간 조용하면(연휴 등) 화면이 멈춘 채로
> 남는다. 운영하면서 이 조합이 실제로 발생하면 `collector/write.js`의
> `runValidationGate`에서 검사 2를 "T1 중 하나가 수집에 성공했다(`ok` 또는 `stale`)"로
> 바꾸는 것을 검토한다. 사양 그대로 구현해 둔 상태다.

### 사내 프록시를 거쳐야 한다면

Node의 `fetch`는 기본적으로 `HTTPS_PROXY`를 보지 않는다. 프록시가 필요한 망이라면
환경 변수를 함께 준다.

```bash
NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://proxy.example.com:3128 npm run collect
```

### 수집 예절

- 조건부 요청(ETag·Last-Modified)을 항상 보낸다. 바뀐 게 없으면 304를 받고 직전 결과를 쓴다.
- User-Agent를 `SecurityWallboard/1.0`으로 명시한다. 기본 UA는 상당수 사이트가 차단한다.
- 동시 요청은 6개로 제한하고 소스별 타임아웃은 10초, 재시도는 1회다.
- Bluesky는 요청 사이에 300ms 간격을 둔다.

### 저작권 경계

표시하는 범위를 제목, 피드가 제공하는 요약, 출처 매체명, 발행 시각, 원문 링크까지로
제한한다. 본문 전문을 가져오지 않는다. 원문 페이지를 새로 요청하는 동작은 구현하지
않았고 사진도 가져오지 않는다.

## 현재 알려진 상태

- **bsky-cve** — Bluesky 공개 API가 데이터센터 IP에 403을 준다. 인증 문제가 아니라
  요청 출처 차단이다. 사내망에서 `npm run verify-sources`로 다시 확인한다.
- **infosec-exchange** — 응답은 200이지만 채널에 `<item>`이 하나도 없는 빈 피드다.
  해당 인스턴스가 비로그인 태그 타임라인을 막아 둔 것으로 보인다.
- 위 둘이 모두 비어 있으면 오른쪽 소셜 열에 "소셜 항목이 없다"가 표시된다.
  T1·T2·T3과 섞지 않는 것이 사양이므로 다른 항목으로 채우지 않는다.
